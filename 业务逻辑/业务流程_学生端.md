# 第一部分：系统概述与核心规则

## 1. 系统概述

本系统服务于 BNBU（北京师范大学-香港浸会大学联合国际学院）的体育 PE 课程管理。核心业务是**学生运动打卡**和**期末成绩查看**。

### 1.1 核心业务规则（全局）

| 规则项           | 值              | 说明                                                  |
| ---------------- | --------------- | ----------------------------------------------------- |
| 总打卡时长       | 教师按教学班设置 | 课程运动与自主其他运动目标之和；管理员不配置学时目标 |
| 课程运动最低     | 由教师自由分配    | 教师端为每个教学班配置课程运动打卡时长目标，可被校队/社团抵扣     |
| 自主其他运动最低 | 由教师自由分配    | 教师端为每个教学班配置自主其他运动打卡时长目标，可被校队/社团抵扣 |
| 每日提交上限     | 2h              | 每日最多申报的打卡时长                                |
| 每日提交次数     | 1 次            | 每个自然日最多成功提交一次打卡；学生当天提交 1 小时后，当天视为已完成一次打卡，不能再次提交                                  |
| 凭证最少数量     | 1 照片或1视频   | 至少提交 1 张照片或 1 个视频                          |
| 凭证最多数量     | 6 照片 + 1 视频 | 最多 6 张照片加 1 个视频                              |
| 运动暂停         | 支持            | 可随时暂停/继续，暂停期间不计入运动时长               |

### 1.2 学生端覆盖

| 端                 | 用户 | 形态                      |
| ------------------ | ---- | ------------------------- |
| **Web 前端** | 学生 / 教师 / 管理员 | 浏览器 SPA                |
| **Android**  | 学生 | 原生 App (Kotlin/Compose) |
| **iOS**      | 学生 | 原生 App (SwiftUI)        |

### 1.3 重要术语

| 术语                   | 说明                                                    |
| ---------------------- | ------------------------------------------------------- |
| **打卡时长**     | 学生提交的运动时长（1h 或 2h）                          |
| **期末审查**     | 教师不再逐条审核打卡，期末集中审查，学期中也可以查看    |
| **课程运动**     | 在体育课程下提交的打卡                                  |
| **自主其他运动** | 自由运动打卡，可用校队/社团认证抵扣（课程运动也可抵扣） |

### 1.4 数据展示原则

> **所有前端展示的数据必须来源于后端返回的真实数据**，不硬编码、不伪造、不假设默认值。

- 学生打卡时长: 来源于数据库中实际存储的学生提交记录
- 学生端成绩页仅展示两项固定内容：1000m/800m 耐力跑分数、打卡学时完成情况
- 抵扣后剩余时长: 来源于教师确认抵扣后的实际计算结果
- 耐力跑换算分数: 来源于管理员配置的换算表 + 学生实际用时
- 学生性别/年龄/年级: 来源于数据库中学生档案信息

### 1.5 隐私合规

- **隐私政策同意**: 学生首次登录时弹窗展示《隐私政策》，必须点击同意才能进入系统。系统记录同意时间和政策版本号
- **GPS 数据保留**: 运动打卡附带的位置信息仅保留 **90 天**，到期自动清除。教师审查时在 90 天内仅可查看脱敏区域地图和路径概览；过后显示"定位数据已过期"，不再显示地图
- **推送通知**: 推送通知不包含个人信息（如姓名、成绩分数），仅发通用通知（如"你的成绩已发布，请登录查看"）
- **数据最小化**: 系统仅收集完成体育打卡和成绩评定所必需的数据，不收集不必要的个人信息

### 1.6 多语言支持

学生端 App 支持**中文（简体）**和**English**双语切换：

- **界面语言**: 导航、按钮、表单标签、提示信息等全部 UI 文本支持中英双语
- **语言检测**: 首次启动根据系统语言自动选择，可在「设置」中手动切换
- **邮件模板**: 系统邮件根据学生语言偏好自动选择中/英文版本
- **数据内容**: 成绩项目名称、课程名称等教师/管理员录入的内容不做自动翻译

### 1.7 国际化学生支持

- **英文界面**: 留学生默认使用英文界面（根据系统语言自动检测），也可在设置中手动切换
- **英文邮件**: 系统邮件模板已支持中英双语，根据学生语言偏好自动选择对应语言版本
- **耐力跑标准**: 留学生同样适用中国国家耐力跑标准——在校学习期间统一要求，不做差异化处理

## 2. 打卡学时规则

学时规则由服务端通过 `GET /api/sport/summary` 返回的 `SportRuleDto` 对象提供。`courseRequired`（课程运动要求）和 `generalRequired`（其他运动要求）均由任课教师在教学班级别设定，`total` 为两项之和；管理员不配置任何学时目标。`dailyLimit`（每日上限）为系统固定校验规则。客户端 `totalCompleted` 计算逻辑：每类学时先按教师课程级配置的学时上限封顶再求和，避免超额学时重复计入总完成量。

## 3. 打卡时间窗

学生只能在所属课程对应的时间窗内打卡。时间窗策略由 `GET /api/student/checkin-time-window` 返回，包含 `windowMode`（`"unavailable"` 时全部阻止）、`dateRangeStart` / `dateRangeEnd`（学期日期范围）、`dailyStartTime` / `dailyEndTime`（每日时段）、`excludedDates`（排除日期列表）、`semesterDeadline`（学期截止日期）。初始状态为 `CheckInTimeWindow.unavailable()`，直到服务端返回权威策略后才解除。

时间窗**按教学班独立生效**：授课教师在本教学班的「课程设置」中维护打卡时间窗，系统**不提供管理员全局默认时间窗**。节假日不自动排除——如需关闭打卡，教师手动修改本教学班的时间窗配置。

# 第二部分：学生账号认证与登录

## 1. 最终规则：无密码登录

学生**不设置传统账号密码**——密码仅适用于教师和管理员角色（`users.password_hash` 字段仅对教师/管理员填充；学生账号无密码，登录仅依赖验证码）。新生从登录页点击「扫码加入课程」，扫描教师二维码并核对课程，填写姓名、学号、性别和年级后确认加入。服务端在一次事务中校验加入凭证、课程状态、资料格式和重复成员关系；成功后立即创建或返回学生身份、`active` 课程成员关系与登录会话，不经过教师审批，并直接进入学生主界面。

首次进入主界面后，学生必须绑定自己的手机号和邮箱。之后退出登录或更换设备时，通过邮箱验证码或手机短信验证码重新登录。

```text
登录页 → 扫码加入课程 → 核对课程 → 填写姓名/学号/性别/年级
→ POST /courses/{courseId}/join
→ 服务端原子校验并创建 student + active membership + session
→ 进入主界面
→ 绑定手机号和邮箱 → 后续使用验证码登录
```

## 2. 登录页与课堂流程

登录页提供三个入口：`[邮箱验证码登录]`、`[手机验证码登录]`、`[扫码加入课程]`。

教师创建教学班并投影有效期为 7 天的二维码。学生确认课程、班级、教师和学期后，填写姓名、学号、性别和年级，客户端向 API 基础路径下的 `POST /courses/{courseId}/join` 提交邀请码。服务端校验成功即返回学生、课程、`active` 成员关系和会话；客户端只接受课程 ID、学生 ID 与成员关系互相一致的成功结果，并立即进入主界面。此流程不创建待审核申请，也没有教师批量确认步骤。

## 3. 联系方式绑定与验证码登录

首次进入主界面显示"请绑定手机号和邮箱，用于退出登录后重新进入账号"。学生分别完成短信验证码和邮箱验证码验证，绑定结果保存到 `studentId`。

验证码有效期 10 分钟，只能使用一次；同一联系方式 60 秒内最多发送一次，并设置每小时发送上限、IP/设备限流和连续输错限制。数据库只保存验证码哈希，不保存明文验证码；登录成功后立即使验证码失效并写入审计日志。

> **Android 端实现**：首次登录后若 `account_status == PENDING_CONTACT_BINDING`，系统在进入主界面之前展示 `ContactBindingScreen`——强制要求绑定手机号和邮箱各一次。两个联系方式均验证通过后 `accountStatus` 刷新为 `ACTIVE`，学生才能进入主界面。发送按钮点击后显示 60 秒倒计时禁用状态。

## 4. 换手机与人工恢复

学生在新手机使用已绑定邮箱或手机号验证码登录，系统恢复原 `studentId`、课程、签到、学时和成绩，并创建新的 `deviceSession`。学生在所有客户端均可正常登录使用，不设设备互踢或登录限制。

如果手机号和邮箱都无法使用，不能仅凭姓名或学号自动登录。学生必须提交恢复申请（`POST /api/v1/student/recovery-requests`），由管理员核对本人身份后绑定新的联系方式。

## 5. 账号与设备分离

```text
studentId      = 学生本人
enrollmentId   = 学生与具体教学班的关系
deviceSession  = 当前设备的登录会话
```

退出登录只撤销设备会话，不删除学生身份、课程关系、签到、学时或成绩。只有已验证并绑定的手机号或邮箱可以签发登录会话，不能根据姓名或学号直接登录。

## 6. 账号状态

账号状态：`PENDING_CONTACT_BINDING`、`ACTIVE`。账号状态与课程关系状态分开管理。

> **Android 端实现**：`AccountStatus` 枚举仅定义 `PENDING_CONTACT_BINDING` 和 `ACTIVE` 两个客户端需要区分的状态。`RECOVERY_REQUIRED` 和 `DISABLED` 为服务端内部状态，客户端统一按 `ACTIVE` 处理——服务端在认证/api层面拦截受限账号。

只有 `student.account_status = ACTIVE` 且当前学期课程成员关系为 `active` 的学生可以正式签到；加入失败、成员关系已移出/退出/停用，或未完成必要联系方式绑定的学生不能产生正式学时。

## 7. 最终用户体验

```text
新生：扫码加入 → 填写资料并确认 → 服务端校验成功 → 进入主界面 → 绑定手机和邮箱
老生：输入邮箱或手机号 → 获取验证码 → 进入主界面
换手机：输入已绑定联系方式 → 获取验证码 → 恢复原账号
联系方式失效：提交恢复申请 → 管理员核验 → 重新绑定
```

## 8. Token 与多设备

| 参数                | 值                                                            |
| ------------------- | ------------------------------------------------------------- |
| Access Token 有效期 | 30d                                                           |
| Token 存储位置      | App: EncryptedSharedPreferences（Android Keystore AES/GCM）  |

允许同一账号同时在 Web + Android + iOS 登录，不互踢。Token 各自独立签发，互不影响。

## 9. 验证码错误限制

| 规则         | 值                         |
| ------------ | -------------------------- |
| 连续失败次数 | 5 次                       |
| 锁定时间     | 15 分钟                    |
| 锁定范围     | 按账号（非 IP）            |
| 解锁方式     | 自动过期 或 管理员手动解锁 |

## 10. 登出行为

仅清本地 Token，服务端不维护会话状态（无状态 JWT）。学生退出登录时调用 `POST /api/v1/auth/logout` 撤销设备会话，但不删除学生身份、课程关系、签到、学时或成绩。

> **Android 端实现**：`logout()` 方法执行：注销 FCM Push Token → 清空会话生成计数 → 清空加密 SharedPreferences 中所有认证数据和 workspace 缓存 → 重置 UI 状态为未认证。退出登录有二次确认对话框。

# 第三部分：学生打卡业务

## 1. 业务目标

学生通过开始运动、结束运动和提交凭证，形成可计入本学期体育学时的运动记录。学生可随时查看已提交记录和累计学时。学生提交打卡后，时长立即计入统计，**不经过**教师逐条"通过/驳回"。

学生打卡分为两个学时类别：

- **课程相关运动**：计入课程运动学时，可由已确认的校队或社团认证抵扣（抵扣不超过教师为该教学班设置的对应目标）。
- **其他运动**：计入自主其他运动学时，可由已确认的校队或社团认证抵扣。

两个类别合计构成该教学班由任课教师设定的体育学时要求。

## 2. 核心业务规则

### 2.1 学时规则

- 任课教师在本人教学班中分别配置课程运动打卡时长目标和自主其他运动打卡时长目标；管理员不配置任何学时目标。
- 该教学班总目标为两类目标之和，学生端按所属教学班同步展示目标值和完成进度。
- 学生端同步展示两个类别的目标值和完成进度。
- 校队/社团认证可抵扣课程运动学时和/或自主其他运动学时，抵扣后各类别完成量不超过该教学班对应的教师配置目标。
- 每个自然日最多成功提交 1 次打卡。
- 每个自然日最多计入 2 小时。
- 学生当天提交 1 小时后，当天仍视为已完成一次打卡，不能再次提交。
- 打卡日期以开始运动时所在的自然日为准。
- 打卡跨越零点时，记录仍归属于开始运动的日期，不占用结束运动日期的次数。

### 2.2 计时与学时换算

- 学生点击"开始运动"后开始计时。
- 运动不足 1 小时，不计入学时，也不能形成成功打卡记录。
- 运动满 1 小时但不足 2 小时，计入 1 小时。
- 运动满 2 小时，计入 2 小时并自动结束本次计时。
- 学时由实际开始时间和结束时间换算，学生不再手动选择 1 小时或 2 小时。

### 2.3 运动暂停

- 运动过程中学生可随时点击"暂停"按钮暂停计时。
- 暂停期间计时器停止走动，不计入运动时长。
- 暂停期间学生仍可使用相机拍摄照片或视频。
- 点击"继续运动"后恢复计时。
- 暂停次数不限，但每次暂停和恢复的时间点均被记录。
- 运动时长 =（结束时间 − 开始时间）− 累计暂停时长。

### 2.4 打卡时间范围

- 学生只能在当前学期已开放的日期和每日时段内开始运动。
- 被排除的日期不能开始新的运动计时。
- 学生在开放时段内已经开始运动后，即使结束时间超过每日开放时段，也可正常结束和提交。
- 学期打卡截止后不能开始或补交新的打卡记录。

### 2.5 多端操作

- 同一学生同一时间只能存在一条进行中的运动计时。
- 学生在一端开始运动后，其他端再次开始时显示"已有进行中的运动记录"。
- 多端同时提交时，以最先成功提交的记录为准。
- 草稿只保存在创建草稿的设备，不在不同设备间同步。

### 2.6 打卡页面界面说明

> **本次版本（v1）不实现**：打卡页面中的**距离**、**配速**、**卡路里**及**运动地图**。打卡页面仅展示与计时、暂停、凭证拍摄和提交直接相关的核心功能。

## 3. 打卡前置条件

学生进入打卡页面时依次完成以下检查：

1. 学生账号处于可正常使用状态，且未被限制打卡。
2. 当前学生存在状态为 `active` 的课程成员关系，且该关系属于当前学期、当前教学班。
3. 当前教学班和所属课程处于开放状态。
4. 当前日期位于本学期允许打卡的日期范围内。
5. 当前时间位于每日允许开始打卡的时段内。
6. 学生在开始运动日期尚无成功打卡记录。
7. 学生当前没有在其他设备上进行中的运动计时。

任一条件不满足时，页面直接说明原因，不进入计时流程。课程加入接口失败时不会生成可打卡的成员关系；`removed`、`exited` 或 `disabled` 成员关系均不能替代 `active` 成员关系。

## 4. 学生正常打卡流程

### 4.1 查看当日状态

学生进入打卡页面后看到：当前学期课程名称和任课教师、课程相关运动和其他运动及总学时的完成进度、今日是否已经成功打卡、当前是否允许开始运动。如存在进行中的运动，显示开始时间、已运动时长和继续进入按钮。

### 4.2 选择打卡类别

- **课程相关运动**：自动关联学生当前学期唯一一门体育课程。记录计入课程相关运动学时。
- **其他运动**：不关联具体课程任务。记录计入其他运动学时。

### 4.3 选择运动项目

学生选择以下一种运动项目：跑步、篮球、足球、羽毛球、游泳、健身、骑行、其他。选择"其他"时，必须填写具体运动名称，最多 32 个字符。

### 4.4 健康安全提醒

每个账号首次进入打卡页面时展示健康安全提醒：

> 请根据自身身体状况适量运动。如感不适应立即停止，必要时及时就医。

学生点击"我知道了"后可继续操作，同一账号后续不重复弹出。

### 4.5 开始运动

1. 记录开始时间。
2. 尝试获取当前位置。
3. 页面进入"运动进行中"状态并持续显示已运动时长。
4. 学生离开页面或应用进入后台时，计时仍按开始时间持续计算。
5. 学生再次进入时恢复显示同一条进行中的运动。

位置信息用于辅助判断运动真实性，不是打卡成立的必要条件。学生拒绝定位、设备无法定位或室内信号不足时，记录标记为"未获取位置"，仍可继续运动和提交。

**运动过程中拍摄**：运动进行中（含暂停期间），学生可随时使用相机拍摄照片或录制视频，作为运动过程的记录。过程中拍摄的照片和视频**仅保存为本地草稿**，不即时上传至服务器。最多可拍摄 **6 张照片草稿**。运动过程中不允许从相册选择已有照片或视频——所有凭证必须通过相机实时拍摄。

### 4.6 结束运动

学生点击"结束运动"后，弹出确认对话框："你确定要结束本次运动吗？"（防误触），包含「取消」和「确认结束」两个按钮。

确认结束后，根据实际运动时长（不含暂停时间）处理：

- **不足 1 小时**：弹出提示"运动时长未满 1 小时，本次不计入有效打卡时长。"不占用当日成功打卡次数。运动过程中已拍摄的照片草稿和视频草稿予以保留，学生在当日开放时段内可继续开始运动。
- **满 1 小时但不足 2 小时**：显示实际运动时长，按 1 小时进入提交环节。
- **满 2 小时**：自动结束并按 2 小时进入提交环节。

学生主动放弃进行中的运动时，本次计时不形成成功记录，也不占用当日次数。放弃时草稿照片和视频自动清除。

### 4.7 补充运动信息

计时结束并达到 1 小时后，学生补充：核对打卡类别和运动项目、其他运动可填写不超过 200 字的运动说明、选择至少 1 个凭证（照片或视频）。可从运动过程中拍摄的草稿和当前环节新拍摄的内容中选择。不允许从相册选择已有照片或视频。最多可提交 **6 张照片 + 1 个视频**。

### 4.8 提交确认

学生提交前看到本次记录摘要，确认打卡类别、运动项目、开始和结束时间、计入学时、凭证数量是否正确，并确认提交内容真实有效。

提交成功后：显示"打卡已记录"、清除本次草稿和进行中状态、记录立即计入对应学时类别、更新首页和打卡记录页的累计学时、当日不再允许提交第二条记录。

## 5. 运动凭证规则

### 5.1 数量与格式

- 每次打卡至少提交 **1 张照片或 1 个视频**
- 最多提交 **6 张照片 + 1 个视频**
- 图片支持 JPG、PNG、WebP、HEIC、HEIF
- 视频支持 MP4、MOV
- 每张图片不超过 8MB
- 单个视频不超过 100MB
- 学生确认提交后，Android 端按实际已写入网络的字节显示图片/视频总上传百分比与已上传容量；上传完成后明确切换为“正在提交记录”。不得使用与真实传输无关的模拟进度。

### 5.2 凭证内容

- 凭证应能反映本次运动项目、运动场景或运动过程
- 凭证不得包含与本次运动无关、侵犯他人隐私或违反校纪校规的内容

### 5.3 拍摄来源规则

> **核心原则**：所有打卡凭证必须通过相机实时拍摄，从源头保证运动凭证的真实性。

| 规则项             | 说明                                                                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| 拍摄时机           | 运动过程中（含暂停期间）和运动结束后**均可**使用相机拍摄                                                                          |
| 相册选择           | **不允许**从相册选择已有照片或视频作为打卡凭证                                                                                    |
| 过程中草稿存储     | 运动过程中拍摄的照片和视频**仅保存为本地草稿**，最多保存 6 张照片草稿                                                           |
| 结束打卡时选择凭证 | 可从以下来源选择：① 运动过程中拍摄的草稿；② 当前环节新拍摄的内容                                                                      |
| 草稿生命周期       | 草稿随本次打卡计时生命周期——主动放弃运动则自动清除；**运动时长不足 1 小时时草稿予以保留**                                         |
| 提交后清理         | 打卡成功提交后，本地草稿自动清除                                                                                                        |

## 6. 草稿规则

- 计时结束后尚未成功提交的内容可保存为草稿。
- Android 端在学生离开页面前自动保存草稿。
- 草稿只保存在当前设备，不计入学时，也不占用每日次数。
- 学生再次进入时可继续完善并提交。
- 草稿提交时仍按开始运动日期检查每日次数和打卡日期范围。
- 学期打卡截止后，未提交草稿不能再转为正式记录。

## 7. 打卡记录与学时展示

### 7.1 学生记录页

学生可查看本人全部成功记录，每条记录展示：运动项目、打卡日期、开始/结束时间、实际运动时长和计入学时、课程相关或其他运动标签、关联体育课程、运动说明、凭证数量和可查看的凭证。

> **Android 端实现**：`CheckInRecord` 数据模型包含：`sportType`、`startTime`/`endTime`（ISO-8601 时间戳）、`actualDurationSeconds`、`remark`（学生备注）、`teacherPublicFeedback`（教师公开反馈）、`teacherInternalNote`（教师内部备注，学生端不展示）。记录详情可播放视频缩略图。

每条正式打卡记录必须绑定以下业务标识（由后端根据登录账号及其 `ACTIVE enrollment` 确定）：

```text
recordId / studentId / enrollmentId / teachingClassId / courseId / teacherId / businessDate
```

### 7.2 学时统计

学生首页分别展示：课程相关运动已完成学时和剩余学时、其他运动已完成学时及校队/社团已确认抵扣学时和剩余学时、本学期总完成学时和总剩余学时。

> **Android 端实现**：`totalCompleted` 采用上限封顶计算——每类学时不超过 `hourRule` 对应上限再求和。`StudentProgress` 区分 `course`/`general`（含抵扣后实际值）和 `rawCourse`/`rawGeneral`（原始打卡值）。

学生成功提交后记录默认有效并立即计入统计，不显示过程状态。

## 8. 教师审查打卡（对学生端的影响）

学生提交打卡后，时长立即计入统计，不经过教师逐条"通过/驳回"。教师对打卡做**全部复核**：调整时长、补录学时。不提供逐条通过/驳回/补材料、AI 查重、状态标签（待审核/已通过等）。

**教师调整打卡时长对学生端影响**：教师期末审查时可将有效记录时长调整为 1 小时或 2 小时，也可作废为 0 小时（该条记录不再计入学时）。调整后学生端有效学时立即更新，发送强制 App 内通知（不可静默）。

**教师补录学时对学生端影响**：教师补录后学生端有效学时和达标进度立即更新，发送强制 App 内通知。教师补录不占用学生"每日 1 次 / 每日 2h"额度。

**被限制打卡对学生端影响**：被限制打卡后，打卡前置条件检查不通过，页面显示原因。

## 9. 异常与边界场景

### 9.1 当日已有成功记录

显示"今日已打卡"，并引导查看当日记录。即使当日已提交记录仅计 1 小时，也不能再次提交。

### 9.2 跨日运动

23:30 开始、次日 00:30 结束的运动按开始日期记录，并计入开始日期的每日次数。

### 9.3 定位不可用

定位失败不阻止计时和提交。记录保留"未获取位置"的事实。

### 9.4 应用退出或设备重启

进行中的运动以已记录的开始时间持续计算。学生重新进入后恢复进行中状态；达到 2 小时时按 2 小时上限处理。

### 9.5 更换设备

学生在另一设备进入时可看到已有进行中的运动，但不能重复开始。应回到原设备结束和提交；原设备不可用时，可放弃本次计时后重新开始。

### 9.6 无当前体育课程

学生没有当前学期 `active` 课程成员关系时，不能发起任何打卡。页面根据实际情况提供明确入口：

- 没有有效成员关系：显示「扫码加入课程」和「输入邀请码」入口
- 二维码/邀请码无效、过期或被撤销：明确说明原因，并提示联系教师获取新凭证
- 课程不存在或已关闭加入：明确说明课程状态，不创建成员关系
- 资料缺失或格式错误：定位到姓名、学号、性别或年级字段，允许原地修正后重试
- 已加入同一课程：不重复创建关系，直接提示并允许进入课程
- 本学期已加入其他课程：阻止第二条 `active` 关系，并提示先联系教师处理原课程
- 网络或服务异常：说明课程尚未加入，保留已填写资料供重试

### 9.7 凭证不合规

凭证数量、格式或大小不符合规则时，学生不能提交。页面明确指出具体文件和原因。

### 9.8 已达到合格打卡时长

学生点击“开始运动”时，后端使用当前 Enrollment 下最新 `VALID` 复核记录的有效计入秒数进行最终判断。累计达到 **20 小时（72000 秒）**且不存在需要恢复的活动会话时，不创建新运动会话，Android 自动提示“已达到合格打卡时长，无需继续打卡”。客户端本地进度只用于提前展示，不能替代后端判断。

教师后续复核导致有效时长重新低于 72000 秒时，学生可再次发起打卡；不得把曾经达标永久缓存为客户端禁用状态。

### 9.9 教师期末处理导致学时不足

教师修正学时后，学生最终有效学时可能低于学期要求。学生记录页展示最新有效学时。

## 10. 隐私与安全

- 首次登录时，学生同意隐私政策后方可使用打卡功能。
- 位置信息只用于辅助判断运动真实性，不用于持续跟踪学生。
- 位置信息保留 90 天，超过期限后教师端显示"位置信息已过期"。
- 学生只能查看自己的记录和凭证。
- 通知内容不直接展示姓名、成绩或运动凭证等个人信息，学生登录后查看详情。

## 11. 完整业务闭环

```text
教师为教学班生成二维码/邀请码
  → 学生扫码或输入邀请码
  → 核对课程、班级、教师和学期
  → 填写姓名、学号、性别和年级并确认加入
  → 服务端原子校验凭证、课程、资料、一学期一课和重复提交
      ├── 校验失败 → 返回精确错误，不创建成员关系
      ├── 已加入同一课程 → 返回既有 active 成员关系，不重复创建
      └── 校验成功 → 创建 student + active membership + session
  → 学生立即进入主界面并完成账号激活
  → 学生进入打卡页
  → 检查账号、时间范围、当日次数、进行中记录和课程归属
  → 选择课程相关运动或其他运动
  → 选择运动项目
  → 开始运动并记录开始时间
  → 运动进行中（可随时暂停/继续；可随时拍照或录像，仅存本地草稿）
  → 学生结束或满 2 小时自动结束
  → 弹出确认对话框（防误触）
  → 根据实际运动时长换算 0、1 或 2 小时
  → 不足 1 小时：提示不计入打卡，草稿保留，可后续继续运动
  → 达到 1 小时后补充说明和凭证（从草稿中选择 + 可新拍摄，至少1照片或1视频，最多6照片+1视频，禁止从相册选择）
  → 学生确认并提交
  → 成功记录立即计入对应学时
  → 学生查看记录和累计进度
  → 学期打卡截止
  → 任课教师集中审查并修正学时
  → 学生查看最终有效学时
```

# 第四部分：课程与学期管理（学生视角）

## 1. 课程管理概述

系统**不启用课程任务模块**（`sport_tasks` 表为预留结构，当前业务流程不使用运动任务）。学生一学期只能有一门 `ACTIVE` 体育课，自主其他运动由该门体育课的授课老师统一负责。

学生加入课程的主入口是教学班二维码或邀请码。二维码和邀请码指向同一条短期加入凭证，只用于定位课程并授权本次加入请求；二维码本身不包含永久密钥，也不在客户端决定是否可加入。只有 `POST /courses/{courseId}/join` 返回完整、一致的成功结果后，学生才成为课程成员。

## 2. 学生加入课程（Join）

```text
教师为本人教学班生成二维码/邀请码
  → 学生扫码或手动输入邀请码
  → 系统显示课程、班级、教师和学期
  → 学生填写姓名、学号、性别和年级
  → 学生点击「确认加入」
  → POST /courses/{courseId}/join（携带 inviteCode）
  → 服务端在单一事务中校验并创建或返回 active 成员关系
  → 客户端安装学生资料、课程、成员关系和会话
  → 立即进入学生主界面
```

课程成员关系状态：

| 状态       | 学生端含义               | 能否打卡或产生学时 |
| ---------- | ------------------------ | ------------------ |
| `active`   | 已加入当前课程           | 是                 |
| `removed`  | 已被教师移出课程         | 否                 |
| `exited`   | 已退出课程（预留状态）   | 否                 |
| `disabled` | 成员关系被系统停用       | 否                 |

本流程不再创建 `course_join_request`，也不存在 `PENDING / REJECTED / NEEDS_CORRECTION` 入课审批状态。加入请求的必填业务字段是姓名、学号、性别、年级和邀请码；邮箱可作为选填资料，但不能替代后续经验证码完成的联系方式绑定，加入过程也不收集学校密码。

服务端必须把「校验凭证—校验一学期一课—按学号查找或创建学生—创建/返回成员关系—签发会话」放在同一事务中，并以学期 + 学生 + 课程唯一约束和幂等键防止双击、重试或并发请求生成重复关系。成功响应至少包含 `student`、`course`、`membership(status=active, joinedAt, joinMethod)` 和可用于进入学生端的 `session/token`；若学生已经加入同一课程，应返回既有关系和 `alreadyJoined=true`，而不是报出不可恢复的重复错误。

失败响应必须区分：凭证无效、凭证过期、凭证已撤销、课程不存在、课程关闭加入、资料格式错误、本学期已有其他 `active` 课程、账号/学号冲突、请求过于频繁、网络异常和服务异常。任何失败都不得留下半创建的学生、成员关系或会话。

一个学生、一个学期，最多只能有一门 `ACTIVE` PE 课。这是课程关系设计的基础规则，由后端和数据库共同校验。

## 3. 学生被移出课程（Remove）

「移出课程」操作由教师在 Web 端执行，学生端不提供自主操作入口。教师二次确认并填写原因后，该课程成员关系从 `active` 变为 `removed`。

移出后学生端的效果：该课程从「当前课程」移到「历史课程」，状态显示「已移出课程」，不能再对该课程提交打卡，历史打卡记录可查看（只读）。

移出后的数据归属：校队/社团抵扣跟随原课程保留且不转移，已打卡时长保留在历史记录中不转移到新课，成绩数据保留在旧课程中并随原成员关系只读展示。

## 4. 学生被移出后加入另一门课

原成员关系变为 `removed` 后，学生可在同一学期直接加入另一门课。旧课程的打卡、抵扣和成绩不转移到新课程，新课进度从零开始。学生端课程列表中新课在「当前学期」，旧课在「历史课程」。

## 5. 学生端课程查看

**当前学期课程**（学生一学期仅有一门）：课程信息（代码、Section、名称、教师）、课程进度（打卡时长完成情况）、课程记录（该课程下的打卡记录）。

**课程加入入口与成员状态**：
- 没有当前课程时，首页显示「扫码加入课程」和「输入邀请码」
- 扫码或输入邀请码后，先显示课程、班级、教师和学期，学生确认后填写姓名、学号、性别和年级
- 加入成功后直接刷新首页、课程列表和登录会话，不展示「加入申请」区域或等待审核状态
- 加入失败时在当前页面显示精确原因并保留可重试资料
- 只有成员关系为 `active` 时打卡入口才可用

**历史课程**（按学期倒序展示）：历史课程列表、课程信息、课程成绩（如已归档）、打卡记录（只读回溯）。

## 6. 学生端新学期数据重置

> **设计动机**：新学期开始时，App 需清除本地缓存的旧学期数据，确保学生看到干净的起点和明确的「扫码加入课程」入口。

### 6.1 总体原则

- **学期切换时服务端不做数据销毁**：学期切换时，所有历史学期数据在服务端保留，仅通过学期状态（`current` → `archived`）实现逻辑隔离。管理员可在完成备份和审批后执行全量业务数据清理。
- **App 端做本地缓存清除**：当 App 检测到新学期开始时，自动清除本地缓存的 workspace 数据，强制从服务端重新拉取。
- **不清除登录态和用户配置**：Token、主题模式、语言偏好等与学期无关的数据保留，学生无需重新登录。

### 6.2 学期切换触发条件

App 端在以下时机执行新学期检测：

| 触发时机                               | 检测方式                                                                                    |
| -------------------------------------- | ------------------------------------------------------------------------------------------- |
| App 冷启动 + 自动恢复会话               | 比较本地缓存的 `currentAcademicYear` 与 `StudentProfile.currentAcademicYear`              |
| 下拉刷新 workspace                     | 同上                                                                                        |
| 从后台切回前台（超过 30 分钟）         | 同上                                                                                        |

当 `本地 currentAcademicYear ≠ 服务端 currentAcademicYear` 且本地值非空时，判定为**新学期开始**。

### 6.3 检测到新学期后的 App 行为

```
App 检测到新学期
  ├── Step 1: 清除本地 workspace 缓存（课程列表、打卡记录、学时进度、通知列表）
  ├── Step 2: 保留 authToken、userProfile、themeMode、appLanguage、隐私政策同意记录
  ├── Step 3: 更新本地 currentAcademicYear 为新值
  ├── Step 4: 从服务端重新加载 workspace
  └── Step 5: Dashboard 自动展示「扫码加入课程」入口
```

### 6.4 本地缓存清除范围

| 清除                                                               | 保留                                           |
| ------------------------------------------------------------------ | ---------------------------------------------- |
| workspace（课程、进度、记录、成绩、通知、memberships、exemptions） | authToken（JWT）                               |
| lastSyncTimestamp                                                  | userProfileJson（基本信息）                     |
| syncOperations 列表                                                | themeMode / appLanguage（用户偏好）             |
| 直接加入流程的临时课程与表单状态                                  | 隐私政策同意记录                               |
| checkInTimeWindow 本地缓存                                         | FCM Push Token 注册状态                        |
| 草稿打卡数据（本机）                                               |                                                |

### 6.5 历史数据查看

学生在新学期仍可通过「课程」标签页 → 历史课程查看过往学期已归档课程的成绩和打卡记录。历史课程数据来源于服务端实时查询（`scope = "history"` 或 `scope = "all"`），不依赖本地缓存，仅供只读查看。

# 第五部分：成绩展示（学生视角）

> **说明**：本部分仅描述学生端可见的成绩展示内容，不涉及教师端的成绩规则配置、录入、发布、归档等操作细节。

## 1. 学生端成绩展示

学生端成绩页仅展示两项固定内容：

| 展示内容            | 说明                                                                                                                                                                                                                           |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1000m/800m 跑步分数 | 教师录入用时后系统按换算表自动换算的百分制分数；成绩未发布时显示"待发布"。**耐力跑状态**分为四种：`Recorded`（已录入）、`Exempt`（免测，显示教师自定义分数）、`Absent`（缺考，计 0 分）、`NotRecorded`（未录入） |
| 打卡学时完成情况    | 当前有效打卡学时及学期要求的剩余学时                                                                                                                                                                                           |

- 成绩发布后，学生端同步展示上述两项内容。
- 三端（Web、Android、iOS）展示内容一致。

> **Android 端实现**：`GradesScreen` 只展示耐力跑成绩和打卡学时完成情况；`EnduranceRunStatus` 是客户端模型层的显式枚举。

## 2. 教师发布成绩（对学生端影响）

教师发布成绩后：学生收到不可关闭的 Push + App 内通知；学生端 `GradesScreen` 展示 1000m/800m 跑步分数（含 `enduranceRunStatus` 状态）和打卡学时完成情况。

教师发布后改分对学生端影响：学生端即时更新，发送成绩变更通知。

## 3. 耐力跑成绩换算（学生端试算工具）

学生端提供耐力跑换算**试算工具**：输入分钟+秒，查看换算分与等级，**不写入**正式成绩。按**性别 + 年级组**查表，共 4 套：男-大一大二、男-大三大四、女-大一大二、女-大三大四。女生 800m，男生 1000m。用时落入表中某秒对应分数（0-100），映射等级：优秀/良好/及格/不及格。越界：用时短于表内最快档→记满分；用时长于表内最慢档→记 0 分。

# 第六部分：免测申请与校队社团认证

## 1. 免测申请与审核

学生可申请两类免除：

1. **耐力跑免测**: 800m / 1000m 耐力跑免测
2. **校队/社团免打卡**: 校队或社团成员申请免打卡

### 1.1 耐力跑免测（800m / 1000m）

```
学生提交申请 → 选择免测类型(800m/1000m，根据性别自动默认) →
  填写理由 → 上传证明（至少1张图片） → 提交 →
    教师审核 → 通过/驳回
    驳回后 → 补充材料重新提交
```

- 免测类型: 800m（女生）/ 1000m（男生）
- 理由: 必填
- 证明: 至少上传 1 张图片（如医院证明）
- 重复检查: 同类型不能有重复待审核申请
- 驳回后可补充材料重新提交
- 通过后学生端 `enduranceRunStatus == Exempt`，展示教师自定义分数

### 1.2 校队/社团免打卡

```
学生提交申请 → 选择类型(校队/社团) → 填写组织名称 →
  填写理由 → 上传证明材料 → 提交 →
    授课老师审核 → 通过/驳回
    通过后 → 教师自定义抵扣时长 + 选择抵扣类型
```

- 类型: 校队免打卡 / 社团免打卡
- 组织名称: 必填（<=128 字）
- 理由: 必填
- 证明: 上传身份证明材料

### 1.3 免测/抵扣的时效与撤销

**耐力跑免测**: 免测学生分数由教师自定义（不再固定为 100 分）。

**校队/社团抵扣**: 抵扣确认后如果学生中途退出校队，不自动撤销。如果学生主动告知教师"该生已退出" → 教师可手动撤回抵扣，学生需重新打卡补足差额。

**免测申请提交次数**: 不设上限。每次被驳回后可补充材料重新提交。

## 2. 校队/社团认证与学时抵扣

学生参加校队或社团可获得打卡时长抵扣。授课老师自定义设置抵扣时长数值，上限为该教学班的学时目标，并可自行选择抵扣类型（课程运动 / 自主其他运动，或两者各分配一部分）。学生端同步展示**扣除抵扣后需要完成的实际打卡时长**。

### 2.1 学生视角

- 查看自己的组织认证状态和抵扣详情
- 查看扣除抵扣后还需完成的实际打卡时长（课程运动还需 Xh，自主其他运动还需 Yh）
- 首页和学习进度中展示的是抵扣后的目标值
- 状态: 待确认 / 认证有效

### 2.2 抵扣规则

- 抵扣时长数值由教师**自定义设置**（上限为该教学班设置的课程运动与自主其他运动目标之和）
- 抵扣类型由教师**自行选择**：可抵扣课程运动、自主其他运动，或两者各分配一部分
- **课程运动与自主其他运动均可被校队/社团认证抵扣**，合计不超过该教学班的教师配置总目标
- 抵扣后学生端**同步展示**需完成的总打卡时长
- 抵扣确认后中途退出校队：**不自动撤销**，需教师手动操作
- **社团负责人不参与其中**，只需要老师审核入社/入校队文件即可

# 第七部分：通知、帮助与客服支持

## 1. 通知系统

### 1.1 通知方式（学生端）

| 通知方式       | 说明                                                   |
| -------------- | ------------------------------------------------------ |
| 学生端通知中心 | 学生在 App 内查看全部个人业务通知                      |
| 移动端 Push    | 面向 Android 和 iOS 学生的时效性提醒（FCM）            |
| 邮件           | 打卡截止提醒、课程取消、计划维护、紧急维护、恢复申请等 |

### 1.2 通知内容

Push 和邮件标题只提示业务事项，不展示成绩分数、学号、健康材料、定位信息、凭证内容或工单正文。用户进入系统后查看具体内容。

与学生相关的通知类型：

| 通知类型             | 触发事项                                               | 通知内容与后续操作                                              |
| -------------------- | ------------------------------------------------------ | --------------------------------------------------------------- |
| 打卡提交确认         | 学生成功提交打卡                                       | 显示提交日期、打卡类型和时长                                    |
| 打卡记录处理         | 教师调整时长                                           | 必须发送 App 内通知（不可静默），显示处理结果和原因说明         |
| 教师补录学时         | 授课教师补录学时                                       | 显示补录学时、学时类型和补录原因                                |
| 打卡窗口变更         | 开放时间、关闭时间或特殊日期调整                       | 显示调整后的时间和生效日期                                      |
| 恢复后的打卡补交     | 只读模式/维护模式结束，学生存在未提交的计时结果         | 提示学生恢复提交                                                |
| 课程成员关系         | 学生直接加入成功，或成员关系被移出、退出、停用         | 显示课程名称、成员状态、加入方式或变更原因                      |
| 课程变更             | 转班、课程取消或授课教师变更                           | 显示课程名称、变更结果和下一步安排                              |
| 成绩规则发布         | 授课教师发布本课成绩规则                               | 通知学生成绩规则已发布                                          |
| 成绩发布             | 成绩发布                                               | 提示登录查看跑步分数和打卡学时                                  |
| 缺考标记             | 教师标记学生缺考                                       | 显示缺考项目和处理结果                                          |
| 免测申请             | 免测申请需补充材料、审核通过或驳回                     | 显示处理结果和下一步操作                                        |
| 校队/社团认证        | 教师审核、认证驳回、抵扣生效或抵扣撤销                 | 显示认证状态、抵扣结果或处理原因                                |
| 账号与权限           | 学生联系方式绑定变更、账号状态变更                     | 显示账号状态和处理入口                                          |
| 归档处理             | 成绩修正审批、学期归档完成                             | 学生接收成绩修正和学期归档完成通知                              |
| 系统公告与维护       | 系统公告、计划维护、紧急维护、系统恢复                 | 显示公告内容、维护时间和恢复状态                                |
| 服务反馈             | 反馈受理、补充信息、状态变更、处理完成或关闭           | 显示工单状态和回复内容                                          |

### 1.3 通知偏好

学生**不可**关闭任何通知。所有通知均强制推送至学生端通知中心。

### 1.4 通知处理流程

业务事项完成后，系统生成对应通知并写入通知中心。学生的时效性事项同时发送移动端 Push。Push 未送达时，通知中心继续保留该事项，用户登录后可查看。同一业务事项只生成一条通知，内容更新时在原通知中更新处理状态和时间。

> **Android 端实现**：`StudentNotice` 模型包含 `targetType` 和 `targetId` 字段，用于导航至免测等具体记录。通知列表通过 `visibleNotices` 过滤后展示，未读计数由 `unreadNoticeCount` 派生。通知可按「全部/截止提醒/申请与材料/组织认证/系统通知」四个类别过滤。

## 2. 学生端引导

学生首次登录后进入四步引导：

1. 加入课程：扫码或输入邀请码，核对课程信息，填写姓名、学号、性别和年级；校验成功后直接进入首页
2. 打卡：课程成员关系为 `active` 后，选择打卡类型，开始运动，结束运动，上传凭证并提交
3. 成绩：查看跑步分数和打卡学时
4. 申请：提交免测申请和校队/社团认证申请

每一步包含页面截图和简要说明。学生可跳过引导，也可在帮助中心重新查看。

## 3. 帮助中心

帮助中心包含常见事项、关键词搜索和操作指引。常见事项覆盖登录与验证码、扫码/邀请码直接加入课程及常见失败原因、打卡、凭证上传、草稿恢复、课程与成绩、免测、组织认证、通知、维护期间操作和服务反馈。帮助内容全部以服务端配置为准，由管理员发布、更新和下线。全部内容中英双语。

## 4. 客服与服务反馈

### 4.1 支持层级

| 层级        | 处理内容                                       |
| ----------- | ---------------------------------------------- |
| L1 自助服务 | 通过帮助中心、常见事项和操作指引自行处理       |
| L2 业务支持 | 授课教师处理本课程打卡、成绩、免测、认证等事项 |
| L3 技术支持 | 管理员提交系统故障和无法解决的事项给开发团队   |

### 4.2 反馈提交

学生通过"设置—服务反馈"提交反馈。反馈内容包括：服务类别、反馈说明、当前页面、客户端版本和系统版本、用户主动上传的截图（最多 3 张）。反馈页面不收集登录凭证、Token、Cookie、完整控制台日志和完整请求内容。

### 4.3 服务时限

| 服务类别                   | 首次响应时间   | 处理时间           |
| -------------------------- | -------------- | ------------------ |
| 无法提交打卡               | 4 个工作小时内 | 1 个工作日内       |
| 维护或服务恢复后的打卡补交 | 4 个工作小时内 | 1 个工作日内       |
| 成绩事项                   | 1 个工作日内   | 3 个工作日内       |
| 账号事项                   | 1 个工作日内   | 1 个工作日内       |
| 功能咨询                   | 2 个工作日内   | 3 个工作日内       |
| 大范围系统故障             | 立即升级处理   | 按故障处理流程恢复 |

# 第八部分：系统维护模式（学生视角）

## 1. 维护模式类型

| 模式           | 学生端效果                                                                     |
| -------------- | ------------------------------------------------------------------------------ |
| **正常** | 全部功能可用                                                                   |
| **只读模式** | 可查看，禁止写入（打卡提交、直接加入课程等写操作均拒绝）                     |
| **维护模式** | 普通用户看到维护页面，无法进入系统                                             |

> **Android 端实现**：系统模式由 `GET /health` 端点返回。`SystemMode` 枚举驱动全局写入控制——非 NORMAL 模式下 `isWriteAllowed` 为 false，拦截打卡提交等写操作。MainActivity 启动时通过 `checkSystemMode()` 获取并更新此策略。

## 2. 维护通知（学生收到的）

| 维护类型         | 提前通知时间 | 通知方式                       |
| ---------------- | ------------ | ------------------------------ |
| **计划内维护** | 48 小时以上  | 系统公告 + 推送                |
| **紧急维护**   | 立即         | 维护页面 + 推送                |
| **维护完成**   | 完成后       | 推送"系统已恢复"               |

## 3. 维护期间数据保护

| 场景                           | 保护规则                                                                   |
| ------------------------------ | -------------------------------------------------------------------------- |
| 正在进行的运动（未结束）       | 计时数据在本地保留，维护结束后恢复计时                                     |
| 只读模式期间点击"结束运动"     | 计时结果在本地保留，系统恢复写入后允许补交，按开始时间所在日期计入当日限额 |
| 正在进行的文件上传             | 断点续传，恢复后从断点继续                                                 |
| 未提交的草稿                   | 本地保留，不丢失                                                           |
